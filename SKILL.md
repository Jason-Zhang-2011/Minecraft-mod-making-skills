# Architectury Mod Project

Use this skill for Minecraft mod repositories created with the [Architectury Template Generator](https://generate.architectury.dev/). Keep the target repository's actual configuration authoritative and leave previous mod projects unchanged.

## Read the bundled guidance

Before modifying the target project, read all four bundled files completely:

1. [references/AGENTS.md](references/AGENTS.md) — Architectury module boundaries and cross-platform rules.
2. [references/OLD-AGENTS.md](references/OLD-AGENTS.md) — detailed version, API, build, resource, and verification discipline.
3. [references/Architectury-instr.md](references/Architectury-instr.md) — the original README specification outline.
4. [references/howtowriteREADME.md](references/howtowriteREADME.md) — the maintained workflow for writing a new mod README and configuring SDKs.

These four files are part of this skill and must remain included when distributing it. Do not silently replace or shorten them.

## Establish scope first

- Resolve the exact new or active project directory named by the user.
- Treat every other mod directory as read-only reference material. Copy useful content into the active project before adapting it; never edit, delete, move, or overwrite an older project.
- Inspect existing changes and instructions before writing. Preserve project-specific requirements that do not conflict with the user's latest request.
- If the user requested documentation only, prepare documentation and supporting license files without implementing gameplay code or claiming builds passed.

## Inspect the generated project

Read the actual `gradle.properties`, settings file, root and module build files, Gradle wrapper, loader metadata, source tree, resources, imports, and existing README. Determine rather than assume:

- Minecraft, Java, Gradle, Loom, Architectury Plugin, and Architectury API versions;
- mappings and mapping patches;
- enabled platforms and included modules;
- Fabric, NeoForge, Forge, or Quilt loader/API versions;
- mod ID, resource namespace, package, Maven group, archive name, and project version;
- the JDK required to run Gradle, the Java compilation target, and the Java version required to run the game.

Do not inherit values from folder names, another mod, memory, or an online example. Verify uncertain APIs against the resolved dependencies or exact-version source before implementation.

## Install the project instructions

For a new generated project, copy the bundled `references/AGENTS.md` and `references/OLD-AGENTS.md` into the project root using those exact filenames. If either target file already exists and differs, inspect and preserve its project-specific instructions instead of blindly overwriting it.

Use `Architectury-instr.md` and `howtowriteREADME.md` as authoring guidance. Copy those two into the target only when the user asks to include the full authoring source set; they must always remain present in this distributed skill.

## Write a complete project README

Write the target `README.md` so a new human contributor and a CLI coding agent can both understand the project without prior conversation. Lead with a plain explanation of what the mod does and why it exists.

Include, as applicable:

- project name, purpose, current state, target Minecraft version, and supported loaders;
- a statement that the project was generated with the Architectury Template Generator;
- explicit instructions to read `AGENTS.md` and `OLD-AGENTS.md` before implementation;
- modification boundaries protecting older projects;
- exact confirmed environment, modules, SDK/JDK requirements, mod ID, package, and artifact names;
- complete gameplay behavior with triggers, values, durations, ranges, exceptions, persistence, multiplayer behavior, and server authority;
- implementation placement in `common` versus loader-specific modules;
- required textures, models, translations, recipes, loot tables, tags, sounds, particles, metadata, and other assets;
- build, installation, usage, commands, recipes, configuration, validation steps, known limitations, and expected release JARs;
- a clear distinction between requested behavior, author-added default decisions, implemented behavior, and unverified work;
- a final-report requirement covering changed files, actual SDK, builds, runtime checks, gameplay checks, packaging, and remaining limitations;
- an MIT license section.

When the user's description is incomplete, turn it into an implementable specification. Fill routine boundaries and failure cases with clearly labeled defaults. Ask about missing choices only when they materially change the main gameplay or legal result. Remove stale placeholders and contradictions after the user answers.

Never present planned functionality as implemented or compilation as gameplay proof.

## Apply the MIT license

Use the MIT License for the skill package and for target mod projects prepared with this workflow unless the user explicitly requests a different license.

For a target project:

- add a standard root `LICENSE` file with the current year and the confirmed copyright holder;
- obtain the holder from explicit user input or reliable project metadata, and ask if it is genuinely ambiguous rather than inventing a legal identity;
- set every enabled loader's license metadata to `MIT`;
- add a README license section linking to `LICENSE`;
- ensure the license is included in distributable JARs and verify it after packaging;
- confirm reused code and assets are compatible with MIT distribution and preserve required attribution.

Do not describe Minecraft, Architectury, Fabric, NeoForge, or third-party assets as being licensed by the project owner.

## Implement with Architectury boundaries

- Put shared gameplay, registries, data, resources, and abstractions in `common` by default.
- Keep Fabric, NeoForge, Forge, and Quilt APIs inside their corresponding modules.
- Keep client rendering and input isolated from dedicated-server initialization.
- Make gameplay results server-authoritative and validate client-originated state.
- Preserve the generated multi-project structure and avoid unrelated migrations or dependency upgrades.
- Add every required non-code resource; compilation alone does not make a content feature complete.

Search the repository and resolved source before writing version-sensitive code. Diagnose from the first meaningful compiler or runtime error and fix from evidence rather than guessing alternate API names.

## Configure the SDK and validate

Before coding, identify the required JDK and confirm the installed version. After coding, set the current project's Gradle JVM, Project SDK, module SDK, Java language level, and Maven JDK only where those settings are actually used. Reload the project after changing them.

Use the generated wrapper. Build every enabled platform that consumes changed common code, then run relevant client, dedicated-server, resource, packaging, and gameplay checks. Inspect the release JARs and distinguish:

- source compilation;
- complete builds;
- loader startup;
- dedicated-server safety;
- interactive gameplay behavior;
- visual correctness;
- release packaging.

Report each category truthfully. State any unverified platform or behavior and why. Do not declare completion until the requested implementation, SDK configuration, documentation, MIT metadata, builds, and proportionate runtime checks are complete.
