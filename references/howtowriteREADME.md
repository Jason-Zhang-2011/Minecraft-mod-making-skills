# 如何为新模组编写 README.md

本文记录用户从 2026-10-11 起约定的模组项目说明编写流程。README.md 主要交给 CLI Codex 阅读，用于指导它实现模组。

## 1. 先查看当前项目

- 用户指定新的或正在开发的模组目录后，先查看现有文件、源代码和配置，再编写 README.md。
- 当前使用 Architectury Template Generator：https://generate.architectury.dev/ 。具体 Minecraft 版本、Java 版本、Loader、依赖和模块必须从当前项目读取，不能固定套用旧项目的版本。
- 检查 `gradle.properties`、`settings.gradle`、各模块构建文件、Gradle Wrapper、平台元数据和已有说明，确认项目实际结构及所需 SDK/JDK 版本。
- 本流程的任务是编写开发说明；除非用户另外要求实现，不因为编写 README 就直接开发模组功能。

## 2. 复制两个规则文件

每次创建新项目，将 workspace 下 `docs` 中的以下两个文件原样复制到新项目根目录：

- `AGENTS.md`
- `OLD-AGENTS.md`

源文件实际使用连字符：`OLD-AGENTS.md`，不是 `OLD_AGENTS.md`。README 中必须使用准确文件名，并明确要求 CLI Codex 在实现前完整阅读这两个文件，尤其不能因为 OLD 字样忽略详细规则。

不要修改 `docs` 中的规则源文件。若目标项目已经存在同名且内容不同的规则文件，先检查并保留已有项目要求，不盲目覆盖。

## 3. 保护之前的项目

- 之前做过的模组只允许查看、参考和复制其中的内容，不能修改、删除、移动或覆盖旧项目的文件。
- 允许修改的是用户当前指定的新模组或正在开发的这一个模组。
- 需要复用内容时，复制到当前项目后再修改；不要使用会连带修改原文件的链接。
- README 中也要写明这个修改范围，让后续 CLI Codex 遵守。
- 用户明确要求单独编辑某份说明文件时，仅修改其指定范围。例如本次只新增本文件，不改其他文件。

## 4. README 必须说明什么

README 要让 CLI Codex 清楚知道：**模组是干什么的、要做什么、怎么做、如何证明做对了。**

至少包括：

1. **模组目的与当前状态**：说明主题、目标玩法、目标平台；区分开发要求与已经实现的功能。
2. **必读规则**：明确要求阅读并遵守本项目 `AGENTS.md` 和 `OLD-AGENTS.md`，提供相对链接。
3. **修改边界**：只修改当前项目，保护其他模组和参考文件。
4. **实际项目配置**：根据当前文件说明版本、Loader、模块及所需 SDK/JDK，不凭目录名或记忆猜测。
5. **功能规格**：写清触发方式、行为、数值、持续时间、范围、例外条件和相关资源。需要合成配方时说明材料、排列及产出数量。
6. **实现方法**：解释共享逻辑与平台适配的位置、客户端与服务端职责、状态保存和必要的性能边界。
7. **资源要求**：根据玩法列出模型、纹理、翻译、配方、声音、粒子、数据和元数据，不能只要求 Java 代码。
8. **验收标准**：逐项验证玩法，分别构建并运行所有启用的平台，检查客户端、专用服务器和相关资源。
9. **完成后交付**：要求更新 README，使其符合最终实现，并报告构建、运行、玩法测试结果和未验证项。

其他组织方式和要求，可以参考 workspace 中之前模组文件夹里的 README.md，以及 `docs` 中的说明和示例。只参考适合当前项目的部分，不复制旧项目的完成声明、版本或测试结果。

## 5. 用户叙述不完整时怎么处理

- 不只是逐字抄写用户的口头需求，要将其整理、补充为清晰、完整、可以实现和验收的规格。
- 合理补齐普通实现细节、边界条件、重复触发、计时、保存重载、多人同步等容易遗漏的情况。
- 明确区分“用户已指定的要求”和“为便于实现补充的默认方案”，不能把自己的设计写成用户明确指定。
- 对影响主要玩法且无法可靠推断的缺失信息，向用户询问，同时先完成不依赖答案的说明部分；未确定项清楚标注，不伪装为定稿。
- 数值必须说明含义。例如水平边长不能默认为半径，辐射范围不能自动等同于爆炸破坏范围，玩家感染时长不能自动等同于污染区寿命。
- 用户随后补充或修改需求时，更新对应规格、资源清单和验收标准，并移除已过时的“待补充”内容，避免前后矛盾。
- 不擅自增加与用户需求无关的大型系统。

## 6. 必须传达给 CLI Codex 的开发原则

- 先阅读规则与当前配置，再搜索现有代码、检查实际依赖和对应版本 API；不凭记忆猜类名、方法名或映射。
- 共享逻辑优先放 `common`，平台专用实现放对应模块；不混用 Fabric、NeoForge 等平台 API。
- 客户端表现与服务端逻辑隔离；专用服务器不能加载客户端渲染类。
- 使用项目自带 Gradle Wrapper，只运行实际存在的任务；不为适配旧代码擅自升级或降级版本。
- 每个启用的平台分别验证；编译通过、游戏启动和实际玩法通过是不同的验证结果，不能相互代替。
- 未执行的测试、未实现的功能和无法验证的平台必须如实说明。

## 7. SDK/JDK 检查与软件配置

每次开始一个新项目，都必须单独检查该项目真正需要的 SDK/JDK 版本，不能沿用上一个模组的版本，也不能只根据目录名或记忆判断。README.md 必须把这项工作写进实现和验收流程。

### 开始编码前

- 从当前项目的 Gradle 构建文件、Java toolchain 或 `sourceCompatibility`、`targetCompatibility`、`options.release`、Gradle Wrapper、Minecraft 版本、Loom／Loader／插件要求和实际依赖中确定所需 JDK。
- 区分以下版本：运行 Gradle 所需的 JDK、编译目标 Java 版本，以及游戏运行所需的 Java 版本。三者可能相同，也可能不同，不能自行假设。
- 检查本机是否安装所需 SDK/JDK，并记录实际安装路径和版本。使用 `java -version`、Gradle JVM 信息及构建输出验证，不能只看 IDE 下拉框中的名称。
- 如果项目使用 Maven，也要检查 Maven Wrapper、编译插件、toolchain 和 `pom.xml` 的实际要求；没有 Maven 配置时不要擅自加入 Maven。
- 如果版本要求不明确，先检查项目依赖和对应工具的官方版本要求，再写代码；不能通过不断切换 SDK 碰运气。

### 代码完成后、宣布完成前

- 根据已经确认的要求，把开发软件中的相关 SDK 设置正确：Gradle JVM、Maven Runner/Importer JDK、Project SDK，以及模块 SDK 或 Java Language Level（如果项目或 IDE 使用这些设置）。需要哪个就改哪个，不存在或未使用的配置不要硬加。
- IDE 设置必须与项目构建配置一致，不能只改软件界面而不检查 Gradle/Maven 实际使用的 Java，也不能只让终端构建成功却留下错误的 Project SDK。
- 设置完成后重新加载或同步 Gradle/Maven 项目，并再次运行相关构建、测试和启动验证。最终报告要写明实际使用的 SDK/JDK 版本，以及调整了哪些设置。
- 只有代码完成、所需 SDK 配置正确、项目同步成功并完成相应验证后，才能宣布任务完成。若因权限、缺少 SDK 或软件不可访问而无法设置，必须明确报告尚未完成的部分，不能声称已经全部完成。
- SDK 设置只针对当前正在开发的新项目；不得为了方便而修改以前模组项目的 SDK 配置。

## 8. 文档完成检查

- 两个规则文件已复制，README 中的文件名与链接正确。
- 版本信息来自当前项目，玩法数值与用户最新要求一致。
- README 已要求检查实际 SDK/JDK 版本，并要求在代码完成后配置当前项目所需的 Gradle JVM、Maven JDK、Project SDK 等相关项目设置。
- 用户要求、补充默认方案和待确认问题清楚区分。
- 功能规格与验收标准对应，没有互相矛盾或过期内容。
- 只修改用户授权的当前项目或指定文档，旧项目保持原样。
- 仅编写文档时，不宣称已实现模组或已通过构建和游戏测试。

具体模组的专属玩法应保留在该项目 README 中，不作为以后每个模组都必须采用的通用规则。
